# 27 — Customer profile personal data: storage, access, and validation

## Status

Accepted

## Context

`Customer` (`backend/app/models/identity/customer.py`) has never stored a name, phone number, or
address — real identity data has deliberately lived only inside Stripe Identity's hosted KYC flow
(ADR 9); only the pass/fail verdict round-trips into Trueup's own database
(`backend/app/services/identity/kyc_service.py`). The frontend now needs a Profile page that shows
and edits more than a bare email address, which means storing the platform's first genuinely
human-identity PII columns. No spec or ADR had picked what gets stored, who can read it, how it's
validated, or how it interacts with root `CLAUDE.md`'s "never log a secret or PII" rule — so this
ADR settles that before the schema changes.

## Decision

### What's stored

Three nullable columns added to `customer`: `display_name`, `phone`, `mailing_address`. Nullable
with no default, because every existing customer row predates these fields and login/session reads
must not break for them — a `NULL` means "never set," not an empty string (an autogenerated default
that backfilled `""` would be indistinguishable from "customer explicitly cleared this field").

Nothing beyond these three. No SSN, no date of birth, no government ID data — those remain
Stripe Identity's responsibility (ADR 9) and are never persisted in Trueup's own tables.

### Read access: self-only

`GET /api/v1/profile` and `PATCH /api/v1/profile` resolve the customer entirely from the session
(`flask.session["_user_id"]`, following `chat.py`'s `_current_customer_id` pattern) — no
`customer_id` request parameter of any kind, so there is no ownership check to get wrong and no
staff/admin bypass. No staff/admin read path exists for this data in this change; if adviser access
to a customer's profile is wanted later, that is a separate, separately-audited decision (it would
need its own justification against the minimum-necessary-access principle, not an incidental
side-effect of this one).

### Never logged, never in an audit payload

`app/core/logging.py` documents the platform's existing mechanism for this: structured logging via
`structlog`, with the stated contract that "secrets and PII never reach a log — this module is the
plumbing; callers keep them out of calls." There is no field-name redaction registry in this
codebase — `password_hash` is kept out of logs the same way: no code path ever passes it to a
logger call or serializes it into a response. Profile PII follows the identical discipline: no
`log.*()` call in the profile service or controller ever receives `display_name`, `phone`, or
`mailing_address` as an argument, structured or otherwise.

The `@audited` decorator (`app/core/security.py`, ADR 15) already enforces this structurally for
audit rows: `AdminAuditLog.payload_hash` stores a SHA-256 hash of the request body, never the body
itself. `PATCH /api/v1/profile` is `@audited("identity.profile.update")`, which records that a
change happened (actor, target customer, timestamp, payload hash) without ever writing the new
name/phone/address values into `admin_audit_log`.

Validation errors reference the field name only, never the submitted value — an error message never
echoes attacker-controlled input back into the response body (output-encoding discipline, root
`CLAUDE.md` security section).

### Retention

No special retention policy. These columns follow the `customer` row's own lifecycle exactly — no
separate TTL, no separate deletion job, no separate export/erasure path beyond whatever governs the
`customer` record as a whole. Stated explicitly so it is not ambiguous later: profile PII does not
get a bespoke retention rule invented in this change.

### Validation rules

- `display_name`: 1–200 characters after stripping leading/trailing whitespace; rejects
  empty-string and whitespace-only input (`None`/omitted is fine — that's "unset," distinct from
  "set to nothing").
- `mailing_address`: 1–500 characters after stripping leading/trailing whitespace; same
  empty/whitespace-only rejection. Free-text single field (street/city/state/zip/country all in
  one) — matches the fact that Trueup validates *identity* through Stripe Identity, not mailing
  address deliverability; no structured address service is introduced by this change.
- `phone`: **E.164** format, exactly — `^\+[1-9]\d{7,14}$` (a leading `+`, then 8–15 digits total,
  first digit non-zero, per ITU-T E.164's own constraint that a subscriber number never starts with
  `0` after the country code). Chosen because it's the one unambiguous machine-checkable phone
  format that needs no per-country parsing library or new dependency, and it's what any future SMS/
  voice provider integration would require verbatim.

Partial update: `PATCH /api/v1/profile` changes only the fields present in the request body: a
present field with a value updates it, a present field explicitly set to `null` clears it, an
absent field is left untouched. No PUT-style full-replace — matches the "safer default for a
profile form" the task called for, and no other PATCH-shaped write exists yet in this codebase to
conflict with.

### Rate limit

`PATCH /api/v1/profile` gets `@limiter.limit("10 per minute")` — the same conservative bound
`funding.py` and `identity.py` apply to every state-changing write in this codebase (`/bank-links`,
`/deposits`, `/withdrawals`, `/kyc-sessions` are all `10 per minute`); a profile edit is no higher-
frequency an action than any of those, and PII changes get no looser a bound than money movement
does. `GET /api/v1/profile` gets `60 per minute`, matching other self-scoped `GET`s
(`/auth/session`, `/funding/history`).

## Consequences

- `customer` gains three nullable `String` columns; every pre-existing row reads back with all
  three `None`, which the view renders as `null` — the frontend must treat `null` as "not yet
  provided," not as an error state.
- A PII change is now an auditable event (`identity.profile.update`), consistent with every other
  privileged/self-service write in this codebase, without adding a second parallel logging/audit
  mechanism.
- Any future adviser-facing read of this data is out of scope here and requires its own ADR —
  this decision does not implicitly grant it.

## Alternatives considered

- **Free-form phone validation (any string).** Rejected: a completely unvalidated phone field is
  useless to any future SMS/voice integration and invites obviously-malformed data with no
  server-side signal. E.164 is the smallest constraint that keeps the field meaningful.
- **A `phonenumbers`-library-backed per-country validator.** Rejected for this change as
  disproportionate: it adds a new dependency and per-region parsing complexity for a field with no
  current downstream consumer beyond display; E.164's own format constraint is sufficient and this
  can be revisited if a provider integration later needs stricter per-region validation.
- **PUT-style full-replace instead of partial update.** Rejected: no other PATCH-shaped write exists
  in this codebase to match, and full-replace would force the frontend to always resend every field
  (including ones the customer isn't editing) just to avoid accidentally clearing them.
- **Allowing staff/admin read in this same change.** Rejected: the task and this ADR scope this to
  self-only; an adviser-facing read is a distinct, separately-audited access-control decision, not a
  natural extension to bundle in here.
- **Structured address fields (street/city/state/zip/country columns).** Rejected for this change:
  no downstream consumer (shipping, tax jurisdiction, etc.) needs structured address data yet, and
  a single free-text field is simplest to satisfy the stated need (show/edit *something* beyond
  email). Revisit if a future feature needs structured address data.
