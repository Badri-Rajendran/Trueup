# Delegating to Codex

## Overview

`codex exec` is a co-equal implementer alongside the in-session `backend-engineer` subagent, not a
fallback — and full-stack: it can take a `backend/` (Flask) or `frontend/` (React) slice. It
writes real files to this repo. Verified against this project 2026-09-05 on a backend baseline
run — see Common Mistakes; the frontend rules below are sourced from `frontend/CLAUDE.md`
directly, not from an observed run.

## The command

```sh
codex exec -m gpt-5.6-terra -c model_reasoning_effort="high" -s workspace-write "$(cat prompt.md)"
```

Every command and path in this skill is relative to the **Trueup repo root**
(`/Users/badrinarayanan/Codes/projects/Trueup`) — run from there, and confirm `pwd` first if a
prior command in the same shell may have `cd`'d elsewhere (shell state persists silently).

Build `prompt.md` from **`prompt-template.md`** in this directory before every delegation — never
write a prompt from scratch. `-s workspace-write` is the whole write-access story: unlike `agy`
(see `delegating-to-agy`), `codex exec` never prompts for per-tool approval, so no further setup
is needed. Never add `--dangerously-bypass-approvals-and-sandbox`. Trueup is already
`trust_level = "trusted"` in `~/.codex/config.toml`.

## Prompt contract

`prompt-template.md` is a positive recipe, in order: task + owning spec section → files to read
first → files owned → files forbidden → the gate → the report shape. **Inline** the owning spec
section and `backend/CLAUDE.md` into the prompt with `$(sed -n '18,45p' docs/specs/N-*.md)` /
`$(cat backend/CLAUDE.md)` rather than only pointing at the paths — the baseline run below never
self-reported reading either file on its own initiative.

## Searching this project

**Backend**: owning spec section → its ADR (why) → `requirements.md` FR/NFR → `app/core/` (the
shared vocabulary every layer uses) → `rg` the four test layers for an existing pattern first.
**Frontend**: `frontend/CLAUDE.md`'s Structure table → the existing `src/features/`,
`src/components/`, `src/hooks/` for a pattern to extend → the component's colocated test file,
if one exists — there is no `docs/specs/`/ADR trail for frontend yet.

## Non-negotiables

Never `git add`/`commit`/`push`/`reset`/`checkout` — the orchestrator commits, always, after
review. Never edit `docs/`. Never touch or log `.env`. Never `uv add`/`npm install` without
asking (frontend's one pre-authorized exception is in `prompt-template.md`). Never weaken a
test, type, or constraint to make something pass. Follow SOLID/DRY/KISS exactly as
`backend/CLAUDE.md` or `frontend/CLAUDE.md` states them — both are pasted into every prompt, so
there is no excuse to skip them. **Never leave an AI/agent attribution mark anywhere** — no
"Generated by", "Co-Authored-By", model name, or similar, in a code comment, docstring, or any
file content (root `CLAUDE.md`'s no-attribution policy, extended here since git is already
forbidden above).

**Red flags in a completion report:** "tests pass" without naming which layers/commands ran (backend:
`mypy --strict`/`ruff check`/`lint-imports` by name; frontend: `npm run lint`/`npm run build`/
`npm test` by name); a test asserting nothing about real behavior; any attribution mark in a
diff.

## Required report shape

Every file changed, with why. Gate output **verbatim**. Which spec/ADR section this implements.
Decisions the spec didn't cover. Anything to double-check. Exact headers in `prompt-template.md`.

## Verify, do not trust

**`-s workspace-write` sandboxes network access — codex genuinely cannot reach PostgreSQL on
localhost.** A GREEN verification run confirmed this: it correctly reported "not done under the
stated definition" and showed the connection failure rather than lying about a full pass. It can
and will run `mypy --strict`, `ruff check`, `lint-imports`, and any pure `tests/unit/` test itself
— it cannot run `tests/integration`/`api`/`contract` or the DB-dependent parts of the suite. So
re-running the gate yourself isn't just discipline here, it's structural: it is the only place the
full suite runs at all.

A completion report is a claim, not evidence — apply `superpowers:receiving-code-review`'s
discipline: restate the claim, check it against `git diff`, never respond performatively.

1. Re-run the gate yourself. Backend, from `backend/`: `uv run pytest -q && uv run mypy --strict
   app && uv run ruff check app tests && uv run lint-imports`. Frontend, from `frontend/`:
   `npm run lint && npm run build && npm test`.
2. Read the whole diff (`git diff --stat` then the real diff), not the report's summary —
   including a check for any attribution mark left in the changed files.
3. Only then stage and commit — only the orchestrator commits.

## Common mistakes

| Observed 2026-09-05 baseline | Fix |
| --- | --- |
| Ran only `pytest tests/unit` ("178 passed"), never touched `integration/`/`api/`/`contract/` | Prompt requires `uv run pytest -q` (whole suite) by name |
| Never ran `lint-imports` — report never mentioned it | Report must show all four gate commands' output |
| No citation of the owning spec/ADR | Report shape requires it as a named field |
